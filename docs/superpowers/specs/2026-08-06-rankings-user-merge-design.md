# 榜单多来源用户合并设计

## 目标

将全服榜与好友榜视为同一套用户数据的不同采集来源。脚本自动获取两份榜单，上传后按赛季和 `userId` 合并为一张全量用户表；页面不提供全服/好友切换。

同时保留现有原始快照和榜单明细，保证历史趋势、审计和后续重算能力不受影响。

## 当前行为与问题

当前 D1 采用两层原始表：

- `rank_snapshots`：每次上传一条快照；
- `rank_entries`：保存该快照里的每个榜单条目。

当前接口的“最新数据”只选择最近的一条快照。如果用户 A 上传后，用户 B 上传一份不同的快照，B 的快照会成为最新快照，A 的用户可能只存在于历史记录中而不出现在当前总览。因此当前实现属于“快照追加”，不是“用户级增量合并”。

## 设计选择

### 方案 A：查询时扫描全部快照

每次读取页面时，扫描所有 `rank_entries`，在 Worker 内按 `userId` 合并。

优点：无需新增聚合表。

缺点：赛季越长、上传者越多，查询成本和延迟持续增长；不同周期的最新值、同小时重复快照和趋势去重逻辑会集中在读取路径，容易超出 D1 查询限制。

### 方案 B：原始快照 + 用户聚合表（采用）

上传时先写入不可变原始快照，再把条目增量合并到按用户维护的聚合表；页面主要读取聚合表，趋势仍读取原始快照。

优点：上传成本可控，用户总览不会被最后一次局部上传覆盖；原始数据完整保留，可随时重建聚合结果。

缺点：需要新增 migration 和上传阶段的合并逻辑。

### 方案 C：只保留用户当前表

直接覆盖用户当前数据，删除或忽略原始快照。

不采用。该方案会破坏已有历史趋势和审计数据，也无法恢复错误上传。

## 数据模型

### 原始层：继续保留

现有表不删除、不覆盖：

- `rank_snapshots` 保留赛季、来源 scope、抓取时间、签名和完整 `raw_json`；
- `rank_entries` 保留快照内的榜单键、用户、数值、排名和原始条目。

全服和好友仍保留各自的 `scope`，但仅用于溯源，不用于页面分组。

### 聚合层：新增

新增按用户和榜单维度维护的当前值表，逻辑主键为：

```text
(season_id, user_id, board_key)
```

每条聚合记录至少包含：

- 用户身份：`season_id`、`user_id`、用户名、头像、VIP 状态；
- 指标：`board_key`、当前值、当前排名；
- 来源：最近抓取时间、最近快照 ID、已见过的 scope；
- 更新时间：首次观测时间和最近观测时间。

用户资料按 `userId` 合并，不创建重复用户。

## 合并规则

### 用户身份

- 只使用 `userId` 作为唯一身份；
- 用户名修改不会生成新用户；
- 全服和好友中出现同一 `userId` 时只保留一行。

### 数值字段

- `epic_*`、`spend_*`、`sets_*` 的相同周期数据不相加；
- 同一用户、同一榜单键多次出现时，采用有效的最新值；
- 对明确只增不减的累计字段，采用观测到的最大值，避免旧快照覆盖新值；
- 同一用户出现在全服和好友榜时，取较新的有效观测；若时间相同则取较大值；
- 某次上传缺少用户或某个榜单字段时，不删除旧值，也不写入 0；前端继续显示为空或已有值。

### VIP 与资料

- `isVip` 只要任一有效来源为 true，就保留 true；
- 用户名、头像和装饰优先使用最近一次非空值；
- source scope 记录为 `global`、`friends` 或两者，供审计使用，页面不做切换。

### 排名

排名不是用户资产，不进行累加或最大值合并。聚合表保存最近一次有效排名；趋势和排名变化仍以原始快照中的排名为准。

## 上传流程

1. 用户脚本分别请求全服榜和好友榜，各请求一次；不增加页面切换。
2. 脚本将成功响应打包上传到同一个 `/api/rankings/snapshots` 请求。
3. Worker 对每份快照独立校验赛季、时间、榜单键和条目格式。
4. 校验通过后，先写入原始快照和明细。
5. 再逐条更新用户聚合表。
6. 两份数据都成功时返回完整同步结果；一份失败时保留成功来源并明确返回部分成功状态。

相同赛季、相同签名的重复上传应视为幂等操作：原始快照不重复写入，聚合表也不重复计算。

## 多用户上传示例

```text
上传 1（全服）：
u001 传说 10，消费 12,000,000,000
u002 传说 4

上传 2（好友）：
u001 传说 12，消费 12,000,000,000
u003 兑换 2
```

合并后的用户总览：

```text
u001 传说 12，消费 12,000,000,000
u002 传说 4
u003 兑换 2
```

`u001` 不会被计算为 22 张传说卡，也不会因为第二次上传没有 `u002` 而被删除。

## 查询与趋势

- 用户总览、运气榜和出卡率从用户聚合层读取，因此可包含所有曾经被上传观测到的用户，而不局限于最后一份前 100；
- 缺少消费榜或欧皇榜的用户仍保留，无法计算的字段返回空值；
- 趋势图继续从 `rank_snapshots` / `rank_entries` 读取原始数据；同一用户在同一时间桶出现多份来源时，按 `userId + boardKey + 时间桶` 去重；
- 原始快照永不删除，即使后续聚合逻辑调整，也可以重新构建聚合表。

## 错误处理与兼容性

- 保留已有旧快照，migration 只新增表和索引，不破坏现有数据；
- 旧的单份 `global` 上传仍然可以被接受并进入聚合表；
- 好友接口参数在实现前先通过已登录 CDK 页面网络请求确认，不能凭猜测写死；
- 一份来源请求失败不影响另一份成功数据入库；
- 任何缺失字段都不按 0 覆盖已有值。

## 验收标准

1. 全服和好友包含同一用户时，页面只显示一行，数值不相加。
2. 不同用户分批上传后，用户总览包含两批用户。
3. 后一次局部上传不会隐藏前一次上传的用户。
4. 重复上传同一签名不会产生重复快照或重复聚合。
5. 既有快照数量和内容保持不变。
6. 趋势图仍能读取旧快照，并对同一时间桶的重复来源正确去重。
7. 单来源失败时，成功来源仍可查询，接口返回部分成功状态。
